# herdr-orchestration レビュー — 参照

## 役割と pane（例）

Herdr 上の live 名は環境依存。logical role は handoff の `reviewer` / requester pane。

| 論理 role               | 例（この workspace）       | 備考                                                               |
| ----------------------- | -------------------------- | ------------------------------------------------------------------ |
| requester / implementer | `${HERDR_WORKSPACE_ID}:p1` | handoff 実行 pane                                                  |
| reviewer worker         | `${HERDR_WORKSPACE_ID}:p2` | `--worker-role reviewer`（または登録したカスタムロール名）の解決先 |

`herdr agent list`（および `herdr-orchestrator role show`）で pane と role の紐づけを確認。Registry の `worker.agent_name`（Role Binding 利用時は `pane_id` が格納済み）と reviewer 自身の `HERDR_PANE_ID`（`pane_id`）または live `agent.name` が一致すること（§11.4）。
※ 本リポジトリのレビュー連携では標準ロール名 `reviewer`（UI 表示は `--label "レビュワー"`）での登録を推奨。日本語ロール名（例: `レビュワー`）で登録している環境では handoff 時に `--to レビュワー` を指定する。

- **GitHub 操作権限とコメント投稿条件**:
  - **コメント投稿条件**: 内部レビューはローカル完結を基本とし、依頼元から明示的に指示された場合（request や instruction での指定）に限り、対象 Finding Issue へレビュー結果をコメント投稿（`gh issue comment`）する。投稿前に Issue 番号・リポジトリ・対象 SHA を確認し、レビューGO を「解決完了」と表現しない。API エラー時はレビュー自体を失敗とせず警告として扱う。
  - **クローズ・変更権限**: Finding Issue のクローズ（`gh issue close`）、再オープン、ラベル変更は、PR マージ後の再検証を完了した依頼元（requester / implementer）のみが実施する。**レビュワー（reviewer）が自律的に Issue の状態を変更することは厳禁とする（クローズ等は依頼元のみが実施）**。

## レビュー Tier（深さ）と差分外波及確認

レビューの深さ（Tier）は、変更の規模と影響度に応じて選択する。Tier は「深さ」を定義するものであり、品質ゲート（反証確認や事実と推論の区別）の省略には使わない。

| Tier                       | 対象                                                              | 主な確認観点                                                                                                                | 必須波及確認              |
| :------------------------- | :---------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------- | :------------------------ |
| **LIGHT**                  | ドキュメントの微小修正、typo 修正、単体コメント修正               | 形式確認、リンク切れの有無、Markdown Lint                                                                                   | **D-1**                   |
| **STANDARD**（既定）       | 通常の機能追加・不具合修正・リファクタリング                      | 仕様準拠、契約、テスト網羅性、回帰防止、境界条件                                                                            | **D-1, D-2, D-3**         |
| **DEEP（深掘りレビュー）** | 状態遷移・並行処理・排他制御・認証/認可・セキュリティ・大規模変更 | **STANDARD の全項目**に加え、契約破壊、暗黙の前提、エラー復旧、競合条件、ミューテーション耐性、セキュリティ境界の徹底深掘り | **D-1, D-2, D-3**（必須） |

### 差分外波及確認項目（D-1〜D-3）の定義

- **D-1（設計書ステータス連動）**:
  PR やコミットが `Closes #N` / `Fixes #N` を含む場合、`git grep "#N"` 等で Issue #N を参照する個別設計書（`docs/herdr-orchestrator-*.md`）を特定し、そのヘッダーのステータスが `実装完了（PR #NN にてマージ済み）` に更新されていることを確認する（正本の一箇所性に基づき、`AGENTS.md` や目次へのステータス重複記述は排除する。リリースバージョン `/ vX.Y.Z` はリリース作業時に追記される）。
- **D-2（CLI・ドキュメント整合）**:
  CLI サブコマンドや引数が変更された場合、該当コマンドの `--help` / usage 出力、`skills/herdr-orchestrator/references/public-cli.md`、各 SKILL 内のコマンド例、および `README.md` の記述が完全一致していることを確認する。
- **D-3（見出し・節名変更の波及）**:
  設計書やガイドラインの見出し・節名を変更した場合、`git grep` でリポジトリ全体を走査し、旧節名を参照したままのリンクや記述が残存していないことを確認する。

## ワイドレビュー（総点検 / 全体点検 / 総チェック）

**ワイドレビュー（総点検）** は、特定 PR のマージ可否判定（Tier: LIGHT / STANDARD / DEEP）とは独立して、**リポジトリ全体を横断して健全性を点検する運用プロトコル** である（`repo-review-helper` では `--tier WIDE` として指定可能だが、PR の合否判定をブロックしない特別な点検種別として扱う）。

- **エイリアス（同義語・トリガー語）**: `ワイドレビュー`、`総点検`、`全体点検`、`総チェック`、`WIDE`、`INSPECTION`
- **目的**: 差分にとどまらず、リポジトリ全体のドキュメント鮮度、設計書ステータス、CLI usage、リンク、Issue、作業領域の健全性を定期または節目に総点検する。
- **実施タイミング**: リリース前、マイルストーン完了時、または人間からの定期指示時。
- **判定と指摘の扱い**: **PR の合否判定（GO / 要修正）をブロックしない**。発見された不整合や改善課題は「Finding Issue 起票候補」としてまとめ、依頼元が [review-finding](../review-finding/SKILL.md) スキルの手順に従って Issue を起票する。

| :------ | :----------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## レビュー判定・品質基準

### 1. 指摘の3分類と重大度・Blocking基準

異なるエージェント間での基準ブレを防ぐため、指摘を以下の3種類に厳格に分類する。重大度と Blocking 判定は別々に管理する。

| 分類                  | 定義                                                                                 | 重大度・扱い                                                                                    |
| :-------------------- | :----------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------- |
| **A. 確認済み不具合** | コード、仕様、テスト、再現手順などから具体的な問題を論理的・客観的に裏付けられるもの | **P0〜P3**（P0/P1 は Blocking、P2 は原則 Non-blocking・例外 Blocking あり、P3 は Non-blocking） |
| **B. 未確認リスク**   | 問題が発生する可能性はあるが、重要な前提条件や再現性が未確認のもの                   | 原則として **要確認事項**（確定不具合とせず調査課題として扱う）                                 |
| **C. 改善提案**       | 現行実装が正常に成立しており、保守性・可読性・診断性・将来の堅牢性を高める提案       | 原則 **P3 / Non-blocking**（確定的不具合として扱わず、Blocking 指定禁止）                       |

#### 重大度と Blocking 判定規則

重大度のみから機械的に Blocking を推測せず、以下の基準と例外規則に従って判定する。

| 重大度 | 基準                                                                       | 標準判定         | 例外規則                                                                          |
| :----- | :------------------------------------------------------------------------- | :--------------- | :-------------------------------------------------------------------------------- |
| **P0** | データ破壊、重大なセキュリティ問題、プロセス停止不能など、直ちに対応が必要 | **Blocking**     | なし                                                                              |
| **P1** | 主要機能の破綻、重大な状態不整合、誤配送、契約違反など                     | **Blocking**     | なし（下記 P1 必須 4 要件を満たす場合のみ）                                       |
| **P2** | 特定条件下でのみ発生する不具合、実運用に影響する設計課題                   | **Non-blocking** | **具体的な重大影響とマージ前修正の必要性が客観的に裏付けられる場合のみ Blocking** |
| **P3** | 軽微な改善、保守性・診断性向上、可読性、ドキュメントの表現統一など         | **Non-blocking** | なし（理由なく Blocking 扱いすることを禁止）                                      |

#### P1 判定の過大評価禁止ルール

指摘を **P1** と判定する場合、以下の 4 要素の明記を必須とする：

1. **具体的な発生条件**: どのような引数、状態、シーケンス、環境下で問題が発生するか。
2. **主要機能・データへの重大な影響**: 何が破綻し、どのような実害が生じるか。
3. **客観的な根拠**: 該当コード、仕様書、テスト結果等の具体的な裏付け。
4. **Blocking が必要な理由**: なぜマージ前に修正が不可欠なのか。

※「追加検証したい」「仕様を明記したい」「より堅牢にしたい」という理由だけで P1 に設定することを禁止する（これらは未確認リスクまたは改善提案に分類する）。

#### P2 の例外的 Blocking 基準

P2 を例外的に **Blocking** と判定する場合、P1 と同様に「具体的な重大影響」および「なぜマージ前の修正が不可欠か（Blocking 理由）」の明記を必須とする。説明できない場合は原則どおり Non-blocking とする。

### 2. 指摘候補に対する反証確認（必須）

指摘を確定・報告する前に、以下の反証問いを必ず確認する：

1. **既存処理での防止**: 呼び出し元、上位層、または別処理のガードによって既に防止されていないか？
2. **失敗条件の成立性**: 指摘する障害・不整合が実際に成立する具体的な入力やシーケンスが存在するか？
3. **実装方式の差異**: 単に実装方式や設計の好みが異なるだけではないか？
4. **要求仕様の充足**: その箇所を修正しなくても、現在の要求仕様や契約を満たしているか？
5. **推奨案の有効性**: 推奨する修正案は、別の副作用や回帰を引き起こさず実際に問題を解消するか？
6. **既存保証の実在性**: 失われたと考える保証や機能は、従来本当に存在・意図されていたものか？（過大保証を前提にしていないか）
7. **別仕組みでの維持**: 呼び出し元や別の処理・パイプラインによって、その保証が実質的に維持されていないか？
8. **要求仕様における必要性**: その保証は現在の要求仕様や段階において本当に不可欠か？意図的な仕様変更やトレードオフではないか？

※ 挙動差分が存在すること自体を直ちに不具合と断定せず、意図的な仕様変更や許容されたトレードオフである可能性を確認する。具体的な実害・影響と客観的根拠がある場合に限り不具合として報告し、確認できない点は「要確認事項」へ分類して安易に P1・Blocking としない。反証を確認できなかった場合も、調査範囲と不確実性を明記し、断定的な不具合報告を避ける。

### 3. 指摘テンプレートと確信度

各指摘には必ず以下の項目を記載する。

- **対象**: `path/to/file:L123`
- **問題**: 何が間違っているか、なぜ問題なのか
- **発生条件**: どのようなシーケンス・引数・環境条件下で発生するか
- **影響**: 発生した場合に具体的に何が起きるか（データ破壊、不整合、クラッシュ等）
- **根拠**: 該当コード、設計書章節アンカー、公式仕様、テスト結果など
- **修正方針**: 推奨する具体的な改訂案
- **Blocking理由**: （P0/P1、または例外的 Blocking の P2 の場合必須）なぜマージ前に対処が不可欠か
- **是正完了条件**: 客観的に成否を判定できるチェックリスト（最低2項目）
- **回帰テスト条件**: 実行すべきテストコマンド（`npm run test:orchestrator` 等）または新規テスト要件
- **維持すべき既存保証**: 修正によって損なわれてはならない既存動作・正常系仕様
- **確信度**:
  - **高**: コード、仕様書、テスト、または最小再現によって具体的に裏付けられている。
  - **中**: 論理的な根拠はあるが、一部の実行時条件やエッジケースが未確認。
  - **低**: 追加調査が必要。**原則として確定的不具合とせず「要確認事項」へ分類する。**

※ GitHub 管理対象レビューで未解決指摘を Finding Issue として起票する際は、[review-finding](../review-finding/SKILL.md) Skill を呼び出して起票前品質バリデーションを実施する。

### 4. 判定の定義と条件

#### 4.1 GO 判定の定義と条件

GO 判定は「問題が一切存在しないことの保証」ではない。
以下を満たす場合に **GO**（マージ可能と判定。GitHub 公式の Approve ではない）とする：

1. 必須のレビュー観点（第1段階：設計整合性、第2段階：批判的不具合探索）を完了した。
2. **未解消の確認済み Blocking 指摘（P0 / P1、および P2 の例外的 Blocking を含む）が 0 件であること。**
3. 未実施の検証（リモートActions実行、特定OS等）を明示した。
4. 重大な未確認リスクがあれば明記・報告した。

※ **P2 の例外的 Blocking 指摘が 1 件でも存在する場合は GO と判定してはならない**。一方、P2 Non-blocking 指摘のみや P3 の改善提案、未確認リスクが存在する場合でも、未解消の Blocking 指摘がなければ他の GO 条件を満たす限り GO と判定できる（残存リスク・改善推奨として記録）。

<a id="review-status-mapping"></a>

#### 4.2 レビュー判定と GitHub コメントメタデータ（Status:）の対応

GitHub 管理対象レビュー（Pull Request レビュー等）において、AI エージェントは常に `--comment`（または `scripts/review-sync.sh comment reviewer --status <Approved|"Changes requested">`）を使用し、コメント本文先頭のメタデータで以下の通り判定を表明する：

| 内部レビュー判定 | メタデータ表記 (`- Status:`)  | 意味・運用                                                                                                                                                  |
| :--------------- | :---------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **GO**           | `- Status: Approved`          | PR の変更内容がマージ可能であることを表明（※ GitHub 公式の Approve ボタン押下およびマージは人間のみが担当）。                                               |
| **要修正**       | `- Status: Changes requested` | 未解消の確認済み Blocking 指摘（P0/P1、例外的 Blocking の P2）への修正対応を要求（※ Non-blocking 指摘のみの場合は他の GO 条件を満たす限り GO と判定可能）。 |
| **NO-GO**        | `- Status: Changes requested` | 設計方針やアーキテクチャの抜本的見直しまたは差し戻しを要求（メタデータは `Changes requested` とし、本文の判定・総評において NO-GO である旨を詳述）。        |

※ **レビューGOとIssueクローズ・コメント投稿条件の厳格な分離**: レビューGOは変更内容がマージ可能であることを示すのみであり、関連する Finding Issue の解決完了を意味しない。レビュワーによるレビュー結果のコメント投稿は依頼元から明示的に指示された場合のみ実行する。また、**Finding Issue のクローズ権限は依頼元（requester / implementer）に限定され、レビュワーが自律的に Issue をクローズ・再オープン・ラベル変更することは厳禁とする（クローズ等は PR マージ後に依頼元が実施）**。

### 5. 実行結果と推論の区別

レビュー結果では、以下の情報の性質を厳格に区別して記載する：

- **実行して確認した事実**: 単体テスト実行、構文チェック、シェルシミュレーション等の直接実行結果。
- **ソースコードを読んで確認した事実**: 実装コードの構文、制御フロー、分岐条件の確認。
- **設計書・公式仕様に基づく判断**: 正本仕様や外部公式ドキュメントに照らした評価。
- **推測または未検証の仮説**: エッジケースの懸念、未実機環境での動作推測。
- ※ **ローカルテスト成功を理由に、リモート GitHub Actions や本番環境での実行成功まで過大保証しない**。

### 6. 再レビュー時の検証方針

再レビュー時は以下を必須で実施する。

1. **前回結果の事前読み込み**: 再レビュー時は、**前回のレビュー記録（`docs/reviews/internal/<instance-id>/RVNNN.md` や `INDEX.md`、または依頼書で指定された前回参照先）から前回の指摘詳細を読み込んで保持する**。
2. **参照不能時の安全措置**: 前回結果が消失している・参照不能な場合は、推測で「対応済み」と断定せず、判定を `検証不能（前回結果参照不可）` とし、理由と確認できた範囲のみを報告する。
3. **前回指摘の再検証とレビューイ Decision の評価**: 各指摘を最新コードおよびレビューイの回答（Decision）に基づいて検証し、以下のいずれかに分類する。
   - `対応済み`: `accept` された指摘が正しく修正され、テスト等で検証されている。
   - `部分対応`: `accept` された指摘の一部が未修正、または不十分。
   - `前回指摘の誤り`: レビューイが `reject` を選択し、提示された客観的反証や意図的仕様が論理的に成立している場合（解消扱いとし、GO を妨げない）。
   - `未対応`:
     - レビューイが `defer` を選択した Non-blocking 指摘で、後続 Issue へのリンク・チケット化が確認された場合（「未対応（後続 Issue #NN へ移管）」として記録し、GO を妨げない）。※ Blocking 指摘（P0/P1、および P2 の例外的 Blocking）の `defer` は原則不可。
     - レビューイが `reject` を選択したが反証が不成立の場合、または未修正の場合（Blocking 指摘であれば要修正を維持）。
   - `検証不能`: 前回記録や根拠が確認できない場合。
4. **回帰不具合の確認**: 修正によって別の問題が発生していないか、関連する状態遷移やエラー処理、既存テストが破綻していないかを確認する。
5. **新規問題の探索**: 新たな差分および周辺コードについて、前回見落とした問題がないか探索する（前回と同じ指摘を根拠なく繰り返さない）。

## レビュー記録（RVNNN.md）（reviewer）

`scripts/repo-review-helper record-save` により `docs/reviews/internal/<instance-id>/RVNNN.md` に原子的保存する。

構成:

<a id="reviewee-response-workflow"></a>

## レビューイ対応ワークフロー（事前トリアージ・Decision 3態・回答フォーマット）

レビュワーから指摘を受領した際、依頼元（レビューイ）がいきなりコード修正に走る問題や、全指摘に無条件で盲従・過剰適合して手戻り（別バグや PR 肥大化）を起こす課題を防ぐため、以下のワークフローと規約を適用する。

### 1. 基本原則（即時修正の禁止と事前トリアージ）

- **即時修正の禁止**: 指摘を受領後、**コードを 1 行も修正する前に必ずチャットで各指摘の評価・Decision 案を人間に提示し合意を得る**。
- **全指摘への盲従禁止**: レビュワーの指摘が常に 100% 正しいとは限らない。要求仕様・既存保証・変更スコープ・費用対効果の観点から客観的にトリアージを行う。
- **修正対象の限定**: 人間と合意した `accept` の項目のみ修正に着手する。`reject` や `defer` と決定した項目についてはコード変更を行わない。
- **複数ラウンド時の差分返信と文脈引き継ぎ（案A×Bミックス）**:
  - ラウンド 2 以降では、既に合意・解消した指摘を無駄にドラフトへ再掲し続けず、「未解決の継続論点および新規指摘」に絞り込んで回答を作成する（GitHub PR ログの雪だるま式肥大化を防止）。
  - スクリプト側で壊れやすい機械的 3-way マージを行わず、エージェントが過去コメント履歴を自律的に参照し、前回決定した `defer` や `reject` の文脈を引き継いで回答を自動補完する（人間の手動コピペ不要）。

### 2. Decision（採否決定）の 3 態

| Decision     | 名称       | 定義と運用規約                                                                                                                                                                                    | コード修正   |
| :----------- | :--------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | :----------- |
| **`accept`** | 採用       | 指摘を受け入れ、この PR / 変更でコードまたは文書を修正する。修正内容と検証コマンドを回答に明記する。                                                                                              | **行う**     |
| **`reject`** | 不採用     | 指摘を採用しない。客観的な理由・反証（[#review-principles](#review-principles) の反証問い等）の明記が必須。                                                                                       | **行わない** |
| **`defer`**  | 保留・延期 | 指摘の価値は認めるが、現在のスコープ外・影響範囲大・後続課題とする。後続 Issue の起票は手順 4 で人間の合意を得た後、[review-finding](../review-finding/SKILL.md) スキルに従って起票・リンクする。 | **行わない** |

### 3. 重大度（P0〜P3）と Decision の対応マトリクス

| 重大度 / 分類                | 標準 Decision            | 許容 Decision                 | 判定・運用の基準                                                                                                                                                                           |
| :--------------------------- | :----------------------- | :---------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **P0 / P1（Blocking）**      | `accept`                 | `reject`（例外）              | 原則として `accept` し修正する。指摘の前提や根拠に客観的な誤り（反証成立）がある場合のみ例外的に `reject`（レビュワーとの十分な協議・合意が必要）。                                        |
| **P2（特定条件・設計課題）** | `accept` または `defer`  | `reject`                      | 本 PR のスコープ内かつ安全に対処可能なら `accept`。スコープ外または抜本的設計見直しが必要なら後続 Issue 化して `defer`。不当な指摘なら `reject`。※ 例外的 Blocking の P2 は原則 `accept`。 |
| **P3（改善提案・軽微）**     | `accept` または `reject` | `defer`                       | 修正の費用対効果、PR 差分の肥大化防止の観点から判断。必須でなければ丁寧に `reject` または別 Issue で `defer`。                                                                             |
| **B（要確認事項）**          | （調査後に決定）         | `accept` / `reject` / `defer` | まず事実関係を調査し、確認結果に基づいて `accept`（不具合確認）、`reject`（問題なし）、`defer`（将来検討）を判断。                                                                         |

### 4. 部分同意・不同意時の代替案提示ルール

レビュワーの指摘を「部分同意」または「不同意（`reject`）」とする場合、単に否定・拒否するのではなく、レビュワーが懸念した問題意識や背景を尊重し、現実的な代替アプローチや妥協案、または後続での対応案を提示する。

### 5. 事前トリアージ提示フォーマット（チャット提示用）

```markdown
## レビュー指摘の事前トリアージと対応方針

レビュワーより N 件の指摘を受領しました。コード修正に着手する前に、各指摘に対する評価と Decision 案を報告します。

### 指摘 1: <指摘見出し> (P1-1)

- レビューイ評価: 同意
- Decision: `accept`
- 対応方針: <修正内容の要約>

### 指摘 2: <指摘見出し> (P2-1)

- レビューイ評価: 部分同意
- Decision: `defer`
- 理由・代替案: <スコープ外の理由、後続 Issue #NN への起票案>

### 指摘 3: <指摘見出し> (P3-1)

- レビューイ評価: 不同意
- Decision: `reject`
- 理由・反証: <反証根拠、既存動作の仕様意図>

---

上記の方針で進めてよろしいでしょうか？（合意後に accepted の項目のみ修正に着手します）
```
