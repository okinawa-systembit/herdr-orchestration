# レビューイ対応手順（指摘への対応・トリアージ・回答作成）

<a id="reviewee-response-workflow"></a>

## 1. 基本原則（即時修正の禁止と事前トリアージ）

レビュワーから指摘を受領した際、依頼元（レビューイ）がいきなりコード修正に走る手戻りや、全指摘への盲従・過剰適合による別バグ誘発・PR 肥大化を防ぐため、以下の規約を適用する。

- **即時修正の禁止**: 指摘を受領後、**コードを 1 行も修正する前に必ずチャットで各指摘の評価・Decision 案を人間に提示し合意を得る**。
- **全指摘への盲従禁止**: レビュワーの指摘が常に 100% 正しいとは限らない。要求仕様・既存保証・変更スコープ・費用対効果の観点から客観的にトリアージを行う。
- **修正対象の限定**: 人間と合意した `accept` の項目のみ修正に着手する。`reject` や `defer` と決定した項目についてはコード変更を行わない。
- **P3（軽微な改善提案）の扱い**:
  - 指摘が P3 のみの場合は判定が GO（LGTM with nits）となる。
  - P3 の修正は再レビュー不要であり、実装・設計担当の自己確認と PR 最終判定コメント等の要約で完結させる。
- **複数ラウンド時の差分返信と文脈引き継ぎ**:
  - ラウンド 2 以降では、既に合意・解消した指摘を無駄にドラフトへ再掲し続けず、「未解決の継続論点および新規指摘」に絞り込んで回答を作成する。
  - スクリプト側で壊れやすい機械的 3-way マージを行わず、エージェントが過去コメント履歴を自律的に参照し、前回決定した `defer` や `reject` の文脈を引き継いで回答を自動補完する。

## 2. Decision（採否決定）の 3 態と対応マトリクス

| Decision     | 名称       | 定義と運用規約                                                                                                                                                                                       | コード修正   |
| :----------- | :--------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------- |
| **`accept`** | 採用       | 指摘を受け入れ、この PR / 変更でコードまたは文書を修正する。修正内容と検証コマンドを回答に明記する。                                                                                                 | **行う**     |
| **`reject`** | 不採用     | 指摘を採用しない。客観的な理由・反証（[criteria.md#refutation-checks](criteria.md#refutation-checks) の反証問い等）の明記が必須。                                                                    | **行わない** |
| **`defer`**  | 保留・延期 | 指摘の価値は認めるが、現在のスコープ外・影響範囲大・後続課題とする。後続 Issue の起票は手順 4 で人間の合意を得た後、[review-finding](../../review-finding/SKILL.md) スキルに従って起票・リンクする。 | **行わない** |

### 重大度（P0〜P3）と Decision の対応マトリクス

| 重大度 / 分類                | 標準 Decision            | 許容 Decision                 | 判定・運用の基準                                                                                                                                                                           |
| :--------------------------- | :----------------------- | :---------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **P0 / P1（Blocking）**      | `accept`                 | `reject`（例外）              | 原則として `accept` し修正する。指摘の前提や根拠に客観的な誤り（反証成立）がある場合のみ例外的に `reject`（レビュワーとの十分な協議・合意が必要）。                                        |
| **P2（特定条件・設計課題）** | `accept` または `defer`  | `reject`                      | 本 PR のスコープ内かつ安全に対処可能なら `accept`。スコープ外または抜本的設計見直しが必要なら後続 Issue 化して `defer`。不当な指摘なら `reject`。※ 例外的 Blocking の P2 は原則 `accept`。 |
| **P3（改善提案・軽微）**     | `accept` または `reject` | `defer`                       | 修正の費用対効果、PR 差分の肥大化防止の観点から判断。必須でなければ丁寧に `reject` または別 Issue で `defer`。P3 のみなら再レビュー不要。                                                  |
| **B（要確認事項）**          | （調査後に決定）         | `accept` / `reject` / `defer` | まず事実関係を調査し、確認結果に基づいて `accept`（不具合確認）、`reject`（問題なし）、`defer`（将来検討）を判断。                                                                         |

## 3. 事前トリアージ提示フォーマット（人間チャット用）

```markdown
## レビュー指摘の事前トリアージと対応方針

レビュワーより N 件の指摘を受領しました。コード修正に着手する前に、各指摘に対する評価と Decision 案を報告します。

### 指摘 1: <指摘見出し> (P1-1)

- レビューイ評価: 同意
- Decision: `accept`
- 対応方針: <修正内容の要約>

### 指摘 2: <指摘見出し> (P2-1)

- レビューイ評価: 部分同意
- Decision: `defer`
- 理由・代替案: <スコープ外の理由、後続 Issue #NN への起票案>

### 指摘 3: <指摘見出し> (P3-1)

- レビューイ評価: 不同意
- Decision: `reject`
- 理由・反証: <反証根拠、既存動作の仕様意図>

---

上記の方針で進めてよろしいでしょうか？（合意後に accepted の項目のみ修正に着手します）
```

## 4. レビューイ回答ドラフトテンプレート（`.input/review/reviewee-draft.md` 用）

※ テンプレート主導アプローチおよび制御値の完全分離（[基本方針: 指針 9](../../../docs/core-principles.md#guideline-9)）に基づき、外側の制御値（送信時に `scripts/review-sync.sh` が自動付与する `<!-- review-sync ... -->` マーカー等）は機械側で処理されます。エージェントは本文に制御値（`Role` / `Round` 等）やマーカーを手書きせず、以下のテンプレートに沿って回答を自由記述として記述します。

```markdown
# レビュー指摘への回答 (PR #<pr_number>)

## 判定に対する応答

レビュワーの判定（<Status>）を確認しました。以下の通り指摘へ対応いたしました。

## 指摘への対応 (Decision: accept / reject / defer)

### <指摘見出し>

- Decision: <accept | reject | defer>
- レビューイ評価: <同意 | 部分同意 | 不同意>
- 対応内容 / 理由:
  <具体的な修正内容、コミット、または反証・代替案・後続 Issue リンク>
```
