# レビューチェックリスト群

<a id="review-scope"></a>

## 1. レビュー Scope チェックリスト

### 1.1 基本確認項目

- [ ] 変更が [実装 INDEX](../../../../docs/herdr-orchestrator-implementation-index.md) の段階と一致
- [ ] Task Registry / 状態遷移の正本は [03-task-registry.md](../../../../docs/herdr-orchestrator/03-task-registry.md) に沿う
- [ ] Herdr 公式仕様と独自設計の境界（[レビューガイドライン](../../../../docs/herdr-agent-review-guidelines.md) §2–4）
- [ ] public CLI のみ Registry 更新（JSON 手編集なし）
- [ ] [設計 §15](../../../../docs/herdr-orchestrator/07-skill-and-implementation.md#sec-15): 破壊的操作を allowlist 前提にしない
- [ ] テスト: `npm run test:orchestrator`（claim は request / response に記載）
- [ ] Markdown 変更時: 設計書なら `npm run format:md` / `check:md`（AGENTS.md）
- [ ] 宣言的成果物（Skill・設計書・設定等）: 規則間の整合性（概念定義の一致、原則と例外の整合、判定条件とテンプレートの整合、矛盾・参照漏れの有無）
- [ ] 既存保証の維持: 変更によって従来保証されていた安全性・正確性・検証範囲・品質ゲートが失われていないか（CI/CD、セキュリティ、データ整合性、並行処理、契約変更等で重点確認）

### 1.2 基本方針（[docs/core-principles.md](../../../../docs/core-principles.md)）チェックリスト

- [ ] **[原則 1（KISS 原則）](../../../../docs/core-principles.md#principle-1)**: 複雑な仕組み・過剰な状態管理・多段フォールバックの排除、標準ファイル操作機能の利用
- [ ] **[原則 2（人間中心の可観測性）](../../../../docs/core-principles.md#principle-2)**: 作業領域の `.input/` 一元化、ブラックボックス排除
- [ ] **[原則 3（車輪の再発明をしない）](../../../../docs/core-principles.md#principle-3)**: `git`、`gh` CLI、Unix 標準コマンド等の既存ツール・公式機能への素直な委譲
- [ ] **[原則 4（依存管理の境界分離）](../../../../docs/core-principles.md#principle-4)**: 配布物（中央 Skill・CLI）のゼロ依存（Python 標準ライブラリと OS 標準コマンドのみ）維持
- [ ] **[原則 5（秘密のインライン渡し）](../../../../docs/core-principles.md#principle-5)**: 認証トークンや鍵の局所化・インライン渡し、平文永続化・ログ漏洩の排除
- [ ] **[原則 6（1つの事実は1か所＋機械検査）](../../../../docs/core-principles.md#principle-6)**: ステータスや設定の多重管理排除、単一正本と機械検査（lint/check）のセット運用
- [ ] **[原則 7（修正ラウンドでスコープを広げない）](../../../../docs/core-principles.md#principle-7)**: レビュー指摘修正コミットへの新機能・大規模移行の混入防止
- [ ] **[指針 8（機械検査とエージェント判断の境界）](../../../../docs/core-principles.md#guideline-8)**: 「ただし〜を除く」2 つ以上の機械検査の禁止、自由文の意味・妥当性判定のエージェント委譲
- [ ] **[指針 9（テンプレート主導と制御値の完全分離）](../../../../docs/core-principles.md#guideline-9)**: 本文への外側ヘッダーや機械制御値の手書き・自動挿入排除
- [ ] **[指針 10（黙って失敗しない）](../../../../docs/core-principles.md#guideline-10)**: 警告の標準エラー出力、テストにおける引数変換だけでなく実際の結果・状態（ファイル内容、終了コード、stderr）の検証

### 1.3 テスト品質（実効性）チェックリスト

- [ ] **Red→Green の実効性**: 修正前のコードで新テストが失敗すること（または変更対象の挙動変化を確実に捉えていること）を確認したか。
- [ ] **実際の結果検証（指針 10）**: アサーションが単なる引数変換やモック呼び出しだけでなく、実際の結果（ファイル内容、Registry 状態、終了コード、stderr）を検証しているか。
- [ ] **異常系・境界値の網羅**: 設計書のテスト計画表（テスト項目一覧）とテスト実装の境界値・異常系ケースが一致しているか。

### 1.4 汎用設計・セキュリティ補足チェックリスト

- [ ] **設計の妥当性**: 代替案と不採用理由、既存データの移行・後方互換性、ロールバック手順が考慮されているか。
- [ ] **スクリプトの安全性**: シェルスクリプトにおけるクォート、引数の安全性、およびエラー時中断（`set -euo pipefail` 等）が適切か。
- [ ] **情報漏洩防止**: 公開物（PR 本文、PR コメント、コミットログ）にローカル絶対パスや内部秘密情報が含まれていないか。

## 2. レビュー Tier（深さ）と差分外波及確認（D-1〜D-3）

レビューの深さ（Tier）は、変更の規模と影響度に応じて選択する。Tier は「深さ」を定義するものであり、品質ゲート（反証確認や事実と推論の区別）の省略には使わない。

| Tier                       | 対象                                                              | 主な確認観点                                                                                                                | 必須波及確認              |
| :------------------------- | :---------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------- | :------------------------ |
| **LIGHT**                  | ドキュメントの微小修正、typo 修正、単体コメント修正               | 形式確認、リンク切れの有無、Markdown Lint                                                                                   | **D-1**                   |
| **STANDARD**（既定）       | 通常の機能追加・不具合修正・リファクタリング                      | 仕様準拠、契約、テスト網羅性、回帰防止、境界条件                                                                            | **D-1, D-2, D-3**         |
| **DEEP（深掘りレビュー）** | 状態遷移・並行処理・排他制御・認証/認可・セキュリティ・大規模変更 | **STANDARD の全項目**に加え、契約破壊、暗黙の前提、エラー復旧、競合条件、ミューテーション耐性、セキュリティ境界の徹底深掘り | **D-1, D-2, D-3**（必須） |

### 差分外波及確認項目（D-1〜D-3）の定義

- **D-1（設計書ステータス連動）**:
  PR やコミットが `Closes #N` / `Fixes #N` を含む場合、`git grep "#N"` 等で Issue #N を参照する個別設計書（`docs/herdr-orchestrator-*.md`）を特定し、そのヘッダーのステータスが `実装完了（PR #NN にてマージ済み）` に更新されていることを確認する（正本の一箇所性に基づき、`AGENTS.md` や目次へのステータス重複記述は排除する。リリースバージョン `/ vX.Y.Z` はリリース作業時に追記される）。
- **D-2（CLI・ドキュメント整合）**:
  CLI サブコマンドや引数が変更された場合、該当コマンドの `--help` / usage 出力、`skills/herdr-orchestrator/references/public-cli.md`、各 SKILL 内のコマンド例、および `README.md` の記述が完全一致していることを確認する。
- **D-3（見出し・節名変更の波及）**:
  設計書やガイドラインの見出し・節名を変更した場合、`git grep` でリポジトリ全体を走査し、旧節名を参照したままのリンクや記述が残存していないことを確認する。

## 3. ワイドレビュー（総点検 / 全体点検 / 総チェック）チェックリスト（A-1〜A-8）

ワイドレビューは、特定 PR のマージ可否判定（Tier: LIGHT / STANDARD / DEEP）とは独立して、**リポジトリ全体を横断して健全性を点検する運用プロトコル**である（`repo-review-helper` では `--tier WIDE` として指定可能。PR の合否判定をブロックせず、Finding Issue 起票候補として整理する）。

- **エイリアス（同義語・トリガー語）**: `ワイドレビュー`、`総点検`、`全体点検`、`総チェック`、`WIDE`、`INSPECTION`

| #       | 点検項目                             | 確認内容と手順                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| :------ | :----------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A-1** | **設計書ステータスと実績の突合**     | ① `npm run check:docs-status` でステータス語彙・単一正本の形式を確認する。② そのうえで各設計書（`docs/herdr-orchestrator-*.md`）の「対象 Issue」がクローズ済みの場合、ステータスが `実装完了（PR #NN にてマージ済み）` であり、リリース済みなら PR 番号とタグバージョンが `git tag --contains <mergeCommit>` と一致するか手動で突合確認する。                                                                                                      |
| **A-2** | **単一正本と目次の整合性**           | `AGENTS.md`、`docs/herdr-orchestrator-design.md`、`docs/herdr-orchestrator-implementation-index.md` の一覧にステータスの重複記述（「実装済み」「対応案」等）がなく、各設計書ヘッダーが唯一の正本となっているか確認する。                                                                                                                                                                                                                           |
| **A-3** | **CLI usage とドキュメントの一致**   | 全サブコマンドの `--help` 出力と、`public-cli.md`、SKILL、README のコマンド例・オプション一覧が一致しているか確認する。                                                                                                                                                                                                                                                                                                                            |
| **A-4** | **相対リンクおよびアンカーの健全性** | `check:md` に加え、主要ドキュメント間の相対リンクおよび `#anchor`（`#sec-N` 等）が実在するか確認する。                                                                                                                                                                                                                                                                                                                                             |
| **A-5** | **バージョン表記の整合性**           | `package.json`、SKILL 定義、最新 git tag のバージョン表記に矛盾がないか確認する。                                                                                                                                                                                                                                                                                                                                                                  |
| **A-6** | **GitHub Issue・PR の健全性**        | クローズ漏れの Finding Issue、マージ済み機能を参照したままの未解決 Issue、放置された draft PR、および作成者が Bot（`<app-slug>[bot]`）でないエージェント作成 PR がないか（読み取り確認のみ、自律的な状態変更は厳禁）。                                                                                                                                                                                                                             |
| **A-7** | **ローカル作業領域の健全性**         | `.input/inbox/` や `.input/review/sent/` に保持期間（30日）を超えて残存している古いファイル（30日以内のファイルは保持期間内のため正常）、`docs/reviews/internal/<instance-id>/INDEX.md` と個別 RV 記録の整合性（[Phase 2 設計書](../../../../docs/reviews/REVIEW_SKILL_PHASE2_DESIGN.md) 参照）、および `herdr-orchestrator role show`（`--global` 含む）で `live` 以外の古い Role Binding（閉鎖済み不要ペイン等）が放置されていないかを確認する。 |
| **A-8** | **放置 TODO・将来課題の棚卸し**      | ドキュメントやコード内に放置された「TODO」「将来対応」「チケット」等の記述を棚卸しし、未起票の課題がないか確認する。                                                                                                                                                                                                                                                                                                                               |
