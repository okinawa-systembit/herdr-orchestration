# review-finding — 参照・テンプレート・バリデーションガイド

本資料は、`review-finding` Skill が GitHub Finding Issue を生成・検証・起票する際の正規フォーマット、判定基準、およびチェックリストを定める。

---

## 1. Finding Issue 正規フォーマット

起票時に使用する Markdown 本文（`--body-file`）は以下の構造に従う。

```markdown
## 指摘概要

<!-- 指摘の簡潔なタイトル・要約（1〜2行） -->

## メタデータ

- **検出元**: Scope Review #<issue_no> または PR #<pr_no>
- **検出コミット**: <commit_sha>
- **重大度**: P0 / P1 / P2 / P3
- **Blocking 判定**: Yes (マージ前是正必須) / No (マージ後対応可)
- **Blocking 理由**: <!-- Blocking: Yes の場合必須。なぜマージ前の修正が不可欠かを明記 -->
- **分類**: 契約違反 / 競合条件 / リソースリーク / 境界値 / エラーハンドリング / 設計整合性 / セキュリティ / その他
- **対象ファイル**: `path/to/file:L123`

## 詳細内容・発生条件

### 該当コード箇所

\`\`\`language
<!-- 該当箇所の抜粋コード -->

\`\`\`

### 発生条件

<!-- どのような引数、状態、シーケンス、環境下で問題が発生するか具体的に記述 -->

### 影響

<!-- 問題が発生した場合に、具体的にどのような実害（クラッシュ、データ破壊、状態不整合等）が生じるか -->

## 反証確認（8つの問い）

1. 既存の処理や上位層で防止されていないか？ → ...
2. 実際に失敗する具体的な条件が成立するか？ → ...
3. 単なる実装方式や好みの違いではないか？ → ...
4. 修正しなくても要求仕様を満たしているか？ → ...
5. 推奨案は実際に問題を解消するか？ → ...
6. 失われたと考える保証や機能は従来本当に存在・意図されていたものか？ → ...
7. 別の仕組みや後続処理でその保証が実質的に維持されていないか？ → ...
8. その保証は現在の仕様で本当に必要か？ → ...

## 推奨される対応方針

<!-- 修正案のコード、アルゴリズム、または方針 -->

## 是正完了条件

- [ ] <!-- 修正完了を客観的に検証できる条件1 -->
- [ ] <!-- 修正完了を客観的に検証できる条件2 -->

## 回帰テスト条件

- **実行テスト**: `npm run test:orchestrator` / `python3 -m unittest ...`
- **新規テスト要件**: <!-- 今回の不具合の再発防止用に追加すべきテストケース -->

## 維持すべき既存保証

<!-- 修正によって損なわれてはならない既存動作・正常系仕様・パフォーマンス等の境界条件 -->
```

## 2. 重大度と Blocking 判定規則

| 重大度 | 技術的基準                                                           | Blocking 標準判定     | Blocking ラベル  | Blocking 必須要件                                                                                                                                                               |
| :----- | :------------------------------------------------------------------- | :-------------------- | :--------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **P0** | データ破壊、重大セキュリティ脆弱性、プロセス復帰不能                 | **Yes (Blocking)**    | `blocking:yes`   | 直ちに対応が必要な実害の明記                                                                                                                                                    |
| **P1** | 主要機能の破綻、重大な状態不整合、誤配送、基本契約違反               | **Yes (Blocking)**    | `blocking:yes`   | P1 必須 4 要件（発生条件、主要機能への重大影響、客観的根拠、Blocking 理由）                                                                                                     |
| **P2** | 特定条件下でのみ発生する不具合、実運用に影響する設計課題・境界値欠落 | **No (Non-blocking)** | なし（例外付与） | 原則はマージ後対応可。**例外的に Blocking: Yes とする公算がある場合は、具体的な重大影響とマージ前修正の必要性（Blocking 理由）の客観的記述が必須（`blocking:yes` ラベル付与）** |
| **P3** | 軽微な改善、保守性・可読性向上、表現統一                             | **No (Non-blocking)** | なし             | **Blocking: Yes は指定禁止**（エラー差し戻し）                                                                                                                                  |

## 3. 起票前品質チェックリスト

`review-finding` エージェントは、`gh issue create` を呼ぶ前にこのチェックリストを内部検証する。

- [ ] 検出元 Scope Issue / PR 番号が記載され、GitHub 上で実在しているか？（Open/Closed 問わず実在すれば可。Closed の自動再オープンは行わない）
- [ ] 検出コミット SHA が記載されているか？
- [ ] 重大度（P0〜P3）と Blocking（Yes/No）が分離して明記されているか？
- [ ] P0 / P1 の場合、Blocking が Yes になっており、`blocking:yes` ラベルが付与対象になっているか？
- [ ] P2 で Blocking: Yes の場合、「Blocking 理由」が客観的・具体的に記述されており、`blocking:yes` ラベルが付与対象になっているか？
- [ ] P3 で Blocking: Yes になっていないか？（指定されていたら差し戻し）
- [ ] 対象ファイル・行番号がリポジトリ内に実在しているか？
- [ ] 具体的な発生条件と影響が記載されているか？（曖昧な推測のみの記載でないか）
- [ ] 8つの反証確認がすべて記載されているか？
- [ ] `## 是正完了条件` に 2 項目以上の Markdown チェックリストが存在するか？
- [ ] `## 回帰テスト条件` に実行すべきテストコマンドまたは新規テスト要件が記載されているか？
- [ ] `## 維持すべき既存保証` に既存の契約・動作維持要件が記載されているか？
- [ ] 既存の Finding Issue と重複していないか？（広域検索および対象パスによるキーワード検索を実施したか）

## 4. 重複確認（Deduplication）ガイド

### 検索手順 (RF-03)

1. **広域検索**:
   ```bash
   gh issue list --label review-finding --state all --limit 300
   ```
2. **対象パス・シンボルのキーワード絞り込み検索**:
   ```bash
   gh issue list --label review-finding --state all --search "<対象ファイル名または関数名>"
   ```
3. **安全側判定**:
   - 取得件数が上限に達した場合や API レスポンスが不完全な場合は、「重複なし」と断定せずに対象パスでの絞り込み検索を必ず実施する。それでも不確実な場合は「重複未検証」として差し戻す。

### 重複とみなす基準

以下のいずれかに該当する場合は、重複と判定する：

1. **原因の同一性**: 対象ファイル・関数において、同一のロジック欠落や例外経路に起因している。
2. **包含関係**: 今回検出された不具合が、既に Open している別 Finding Issue の解決によって同時に解消される。
3. **副作用・同根バグ**: 同一 PR / コミット内の同一リファクタリングに起因する一連の軽微な問題。

### 重複検出時のアクション (RF-05)

- 重複と判定された場合は、**新規 Issue の起票を中止（差し戻し/保留）**し、重複対象の Issue 番号および判断根拠をレビュー担当へ報告する。
- **既存 Issue へのコメント追記は自動実行しない**。利用者の明示的な指示または承認がある場合のみ実施する（誤判定による情報混入の防止）。
- 重複が疑われるが独立起票すべきか判断がつかない場合は、起票を保留してレビュー担当エージェントまたは人間に確認を求める。

## 5. Finding 解決完了チェックリスト（2段階分離）

チェックリストの循環依存を防止するため、**Phase 1（実行可否判定）** と **Phase 2（状態更新と事後確認）** を分離して検証する。

### Phase 1: 完了処理の実行可否判定チェックリスト（事前判定）

以下の全項目にチェックが入る場合のみ、Phase 2（ラベル更新・クローズ操作）へ進むことができる。

- [ ] 対象 Finding に対応する修正 PR の番号と URL が特定されているか？
- [ ] 修正 PR がマージ済み（Merged）となっているか？（Open の状態でのクローズ・`status:verified` 付与は禁止）
- [ ] マージ先ブランチ（`main` 等）とマージコミット SHA を確認したか？
- [ ] マージコミット SHA に対して単体テスト・全体自動テスト（`npm run test:orchestrator` 等）が実行され、合格しているか？
- [ ] Finding Issue 本文に記載された「是正完了条件」の全項目（`- [ ]`）が客観的に達成されているか？
- [ ] 「維持すべき既存保証」が損なわれていないか（回帰がないか）？
- [ ] 再検証結果、対象マージコミット SHA、テスト合格実績が Finding Issue にコメントとして記録されているか？

> [!CAUTION]
> Phase 1 の項目が 1 つでも未達成の場合、Phase 2 のラベル更新やクローズ処理を実行してはならない。

### Phase 2: 状態更新と事後確認チェックリスト（事後検証）

Phase 1 達成後、状態更新を実行し、最終的な Issue 状態を機械的に確認する。

- [ ] `status:ready-to-fix` ラベルが削除されたか？
- [ ] `status:verified` ラベルが付与されたか？
- [ ] Issue が Closed になったか？（手動クローズ実行、または自動クローズ正常発生の確認）
- [ ] （自動クローズ方式の場合）PR マージ後に `gh issue view` で実際の状態を取得し、Open のままだった場合に自動クローズ不発として手動クローズへフォールバックしたか？（Open のまま `status:verified` だけ付与された不完全状態を防止したか？）
- [ ] `gh issue view <issue_no> --json state,labels` による再取得で、`state: CLOSED` かつ `status:verified` ラベルが存在することを最終確認したか？
- [ ] 途中で失敗した場合、完了成功と報告せず、現在の状態と未完了操作を人間に報告したか？

## 6. 再検証結果コメント・テンプレート

マージ後の再検証完了時に Finding Issue へ投稿する標準コメントフォーマット：

```markdown
## 是正再検証結果（解決完了）

- **対応 PR**: #<pr_no> (<pr_url>)
- **マージ先ブランチ**: `main`
- **マージコミット SHA**: `<merge_commit_sha>`
- **再検証実施日**: YYYY-MM-DD
- **再検証結果**: 合格 (PASSED)

### 是正完了条件の達成確認

- [x] <!-- 是正完了条件1の内容と確認結果 -->
- [x] <!-- 是正完了条件2の内容と確認結果 -->

### 実行テスト結果

- `npm run test:orchestrator`: XXX passed (OK)
- `python3 -m unittest <test_path>`: OK

### 判定とステータス更新

全完了条件および回帰テストの通過を確認したため、本 Finding は是正完了と判定します。
`status:ready-to-fix` を削除し、`status:verified` を付与して Closed とします。
```

## 7. クローズ方式別の運用比較ガイド

| 項目                      | 手動クローズ方式（標準）                                            | GitHub 自動クローズ方式                                                    |
| :------------------------ | :------------------------------------------------------------------ | :------------------------------------------------------------------------- |
| **位置づけ**              | **標準運用**（原則こちらを使用）                                    | 許容（PR 本文に明示指定がある場合のみ）                                    |
| **PR 本文の記述**         | `Refs #36` 等（非クローズ型）                                       | `Closes #36` 等（自動クローズ型）                                          |
| **PR マージ前の Issue**   | Open (`status:ready-to-fix`)                                        | Open (`status:ready-to-fix`)                                               |
| **PR マージ直後の実状態** | Open (`status:ready-to-fix`)                                        | **要実状態取得**: Closed（正常）または Open（自動クローズ不発）            |
| **再検証の手順**          | マージコミットで検証 → コメント記録 → ラベル更新 → `gh issue close` | マージコミットで検証 → コメント記録 → ラベル更新（`status:verified` 付与） |
| **自動クローズ不発時**    | 該当なし（常に手動）                                                | **手動クローズへフォールバック**（Open のまま放置を厳禁）                  |
| **再検証失敗時の挙動**    | Open のまま再修正へ                                                 | Closed の場合は直ちに `gh issue reopen`、Open の場合はそのまま維持         |
| **Global GO Gate 判定**   | 未検証 Closed が発生しないため安全                                  | 再検証前は未検証 Closed として自動検出・保留される                         |
