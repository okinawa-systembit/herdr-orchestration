# review-finding — 参照・テンプレート・バリデーションガイド

本資料は、`review-finding` Skill が GitHub Finding Issue を生成・検証・起票する際の正規フォーマット、ラベル対応、およびチェックリストを定める。重大度（P0〜P3）・Blocking 判定規則・GO 条件・反証確認の定義正本は **[repo-review/references.md#review-principles](../repo-review/references.md#review-principles)** を参照する。

---

## 1. Finding Issue 正規フォーマット

起票時に使用する Markdown 本文（`--body-file .input/tmp/finding-<id>.md`）は以下の構造に従う。

```markdown
## 指摘概要

<!-- 指摘の簡潔なタイトル・要約（1〜2行） -->

## メタデータ

- **検出元**: PR #<pr_no> または Issue #<issue_no>
- **検出コミット**: <commit_sha>
- **重大度**: P0 / P1 / P2 / P3
- **Blocking 判定**: Yes (マージ前是正必須) / No (マージ後対応可)
- **Blocking 理由**: <!-- Blocking: Yes の場合必須。なぜマージ前の修正が不可欠かを明記 -->
- **分類**: 契約違反 / 競合条件 / リソースリーク / 境界値 / エラーハンドリング / 設計整合性 / セキュリティ / その他
- **対象ファイル**: `path/to/file:L123`

## 詳細内容・発生条件

### 該当コード箇所

\`\`\`language
<!-- 該当箇所の抜粋コード -->

\`\`\`

### 発生条件

<!-- どのような引数、状態、シーケンス、環境下で問題が発生するか具体的に記述 -->

### 影響

<!-- 問題が発生した場合に、具体的にどのような実害（クラッシュ、データ破壊、状態不整合等）が生じるか -->

## 反証確認（8つの問い）

1. 既存の処理や上位層で防止されていないか？ → ...
2. 実際に失敗する具体的な条件が成立するか？ → ...
3. 単なる実装方式や好みの違いではないか？ → ...
4. 修正しなくても要求仕様を満たしているか？ → ...
5. 推奨案は実際に問題を解消するか？ → ...
6. 失われたと考える保証や機能は従来本当に存在・意図されていたものか？ → ...
7. 別の仕組みや後続処理でその保証が実質的に維持されていないか？ → ...
8. その保証は現在の仕様で本当に必要か？ → ...

## 推奨される対応方針

<!-- 修正案のコード、アルゴリズム、または方針 -->

## 是正完了条件

- [ ] <!-- 修正完了を客観的に検証できる条件1 -->
- [ ] <!-- 修正完了を客観的に検証できる条件2 -->

## 回帰テスト条件

- **実行テスト**: `npm run test:orchestrator` / `python3 -m unittest ...`
- **新規テスト要件**: <!-- 今回の不具合の再発防止用に追加すべきテストケース -->

## 維持すべき既存保証

<!-- 修正によって損なわれてはならない既存動作・正常系仕様・パフォーマンス等の境界条件 -->
```

## 2. 重大度・Blocking 判定と GitHub ラベルの対応規則

重大度（P0〜P3）と Blocking 判定の基準正本は **[repo-review/references.md §1](../repo-review/references.md#review-principles)** に従う。Finding Issue 起票時のラベル付与規則は以下の通りとする：

| 重大度 | Blocking 標準判定     | 必須ラベル                   | `blocking:yes` ラベル付与条件                                                            |
| :----- | :-------------------- | :--------------------------- | :--------------------------------------------------------------------------------------- |
| **P0** | **Yes (Blocking)**    | `review-finding,severity:p0` | **常に付与**                                                                             |
| **P1** | **Yes (Blocking)**    | `review-finding,severity:p1` | **常に付与**（P1 必須 4 要件の明記を確認）                                               |
| **P2** | **No (Non-blocking)** | `review-finding,severity:p2` | 原則なし。**例外的 Blocking の理由が客観的に明記されている場合のみ `blocking:yes` 付与** |
| **P3** | **No (Non-blocking)** | `review-finding,severity:p3` | **付与禁止**（`Blocking: Yes` 指定時は起票せず差し戻し）                                 |

## 3. 起票前品質チェックリスト

`review-finding` エージェントは、`gh issue create` を呼ぶ前にこのチェックリストを内部検証する。

- [ ] 検出元 PR / Issue 番号が記載され、GitHub 上で実在しているか？（Closed の自動再オープンは行わない）
- [ ] 検出コミット SHA が記載されているか？
- [ ] 重大度（P0〜P3）と Blocking（Yes/No）が [repo-review/references.md §1](../repo-review/references.md#review-principles) に整合して明記され、上記 §2 のラベル付与条件と一致しているか？
- [ ] 対象ファイル・行番号がリポジトリ内に実在しているか？
- [ ] 具体的な発生条件と影響が記載されているか？（曖昧な推測のみの記載でないか）
- [ ] [8つの反証確認](../repo-review/references.md#refutation-checks)がすべて記載されているか？
- [ ] `## 是正完了条件` に 2 項目以上の Markdown チェックリストが存在するか？
- [ ] `## 回帰テスト条件` に実行すべきテストコマンドまたは新規テスト要件が記載されているか？
- [ ] `## 維持すべき既存保証` に既存の契約・動作維持要件が記載されているか？
- [ ] 既存の Finding Issue と重複していないか？（広域検索および対象パスによるキーワード検索を実施したか）

## 4. 重複確認（Deduplication）ガイド

### 検索手順 (RF-03)

1. **広域検索**: `gh issue list --label review-finding --state all --limit 300`
2. **対象パス・シンボルのキーワード絞り込み検索**: `gh issue list --label review-finding --state all --search "<対象ファイル名または関数名>"`
3. **安全側判定**: 取得件数が上限に達した場合や API レスポンスが不完全な場合は、対象パスでの絞り込み検索を必ず実施する。それでも不確実な場合は「重複未検証」として差し戻す。

### 重複とみなす基準とアクション (RF-05)

- 同一ファイル・関数の同一ロジック欠落、既存 Open Finding の解決に包含される問題、または同一リファクタリング起因の同根バグは重複と判定する。
- 重複と判定された場合は**新規 Issue の起票を中止（差し戻し/保留）**し、重複対象の Issue 番号および判断根拠を報告する（既存 Issue への自動コメント追記は行わない）。

## 5. Finding 解決完了チェックリスト（エージェント再検証と人間クローズの分離）

> [!IMPORTANT]
> **クローズ・ラベル変更権限（人間のみ）**:  
> Finding Issue のラベル更新（`status:verified` 付与等）、クローズ（`gh issue close`）、および再オープン（`gh issue reopen`）は **人間のみが実施する**（正本: [repo-workflow §7](../repo-workflow/SKILL.md#github-write-matrix)）。エージェントによる Issue 状態・ラベルの変更は厳禁とし、エージェントは下記 Phase 1 の再検証と結果記録・人間への報告までを担当する。

### Phase 1: エージェントによるマージ後再検証チェックリスト

人間による PR マージ後、依頼元エージェントは以下の全項目を確認し、再検証結果コメントを記録する。

- [ ] 対象 Finding に対応する修正 PR の番号と URL が特定されているか？
- [ ] 修正 PR がマージ済み（Merged）となっているか？
- [ ] マージ先ブランチ（`main` 等）とマージコミット SHA を確認したか？
- [ ] マージコミット SHA に対して単体テスト・全体自動テスト（`npm run test:orchestrator` 等）が実行され、合格しているか？
- [ ] Finding Issue 本文に記載された「是正完了条件」の全項目（`- [ ]`）が客観的に達成されているか？
- [ ] 「維持すべき既存保証」が損なわれていないか（回帰がないか）？
- [ ] 再検証結果、対象マージコミット SHA、テスト合格実績、および人間向けのクローズ推奨案内がコメントとして記録されているか？

### Phase 2: 人間による状態更新（参考）

Phase 1 の報告確認後、人間が以下を実施する：

- `status:ready-to-fix` ラベルの削除と `status:verified` ラベルの付与
- Issue のクローズ（`Refs #N` 方式の場合。`Closes #N` でマージ時に自動クローズ済みの場合はラベル更新のみ、再検証失敗時は Re-open）

## 6. 再検証結果コメント・テンプレート

マージ後の再検証完了時に Finding Issue へ記録（または人間に提示）する標準コメントフォーマット：

```markdown
## 是正再検証結果（解決確認）

- **対応 PR**: #<pr_no> (<pr_url>)
- **マージ先ブランチ**: `main`
- **マージコミット SHA**: `<merge_commit_sha>`
- **再検証実施日**: YYYY-MM-DD
- **再検証結果**: 合格 (PASSED)

### 是正完了条件の達成確認

- [x] <!-- 是正完了条件1の内容と確認結果 -->
- [x] <!-- 是正完了条件2の内容と確認結果 -->

### 実行テスト結果

- `npm run test:orchestrator`: XXX passed (OK)
- `python3 -m unittest <test_path>`: OK

### 判定とクローズ推奨（人間確認用）

全完了条件および回帰テストの通過を確認したため、本 Finding の是正完了を確認しました。
人間による最終確認の上、`status:ready-to-fix` の削除・`status:verified` の付与および Issue クローズをお願いします。
```

## 7. PR リンク方式別の比較ガイド

| 項目                    | 非クローズ型参照方式（Finding Issue 標準）                          | GitHub 自動クローズ方式（通常 Issue 標準 / Finding 特例）                   |
| :---------------------- | :------------------------------------------------------------------ | :-------------------------------------------------------------------------- |
| **対象と位置づけ**      | **Finding Issue の標準運用**（マージ後再検証を経て人間がクローズ）  | **通常の設計・実装 Issue の標準**（Finding は人間の明示指示時のみ）         |
| **PR 本文の記述**       | `Refs #<FindingIssue番号>`                                          | `Closes #<Issue番号>`                                                       |
| **PR マージ直後の状態** | Open (`status:ready-to-fix`)                                        | Closed（GitHub によりマージ時に自動クローズ）                               |
| **マージ後の手順**      | エージェントが再検証・コメント記録 → **人間がラベル更新＆クローズ** | （Finding の場合）エージェントが再検証・コメント記録 → **人間がラベル更新** |
| **再検証失敗時の対応**  | Open のまま再修正へ                                                 | エージェントが失敗を報告 → **人間が Issue を Re-open**                      |
